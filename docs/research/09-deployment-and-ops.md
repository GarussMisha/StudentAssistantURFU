## 1. Контекст и цель

Стенд должен быть развёрнут и доступен проверяющему без ручных действий
администратора. Домен, HTTPS, оркестрация и мониторинг для учебного проекта —
не самоцель: приоритет — работающий сервис с понятной процедурой запуска,
обновления и отката.

Документ фиксирует: топологию, compose для прода, внешние зависимости (LAN-модели),
процедуру деплоя, откат, `scripts/deploy.sh`, риски и что сознательно отложено.

## 2. Факты из кодовой базы

- `docker-compose.yml`: `postgres`, `qdrant`, `migrate`, `app` (`8000:8000`,
  `extra_hosts: host.docker.internal`), `caddy` (профиль `prod`, 80/443).
- **F-03:** `deploy/Caddyfile` отсутствует — профиль `prod` нерабочий.
- **F-06:** корпус смонтирован именованным томом `kb_data`, хост-файлы
  `data/kb/raw/` в контейнере не видны.
- У `app` нет healthcheck; `restart:` нет ни у одного сервиса; лимитов и
  лог-ротации нет.
- Бэкапов, мониторинга и инструкции восстановления нет.
- Оборудование: домашний сервер 12 ядер, 16 ГБ RAM, **без GPU** (07).
  LLM и эмбеддинги — на другом ПК в локальной сети.
- 02 PR-08: эмбеддинги локальные; удалённый провайдер допустим через `.env`.
- 03 §5.4: `COOKIE_SECURE=true` по умолчанию, `DEBUG=false`; `SUPPORT_EMAIL`
  (07 D-26).
- README до 2026-11-25 обещал HTTPS; исправлен — D-33 закрыт (доступ по IP).

## 3. Топология

```
        интернет / локальная сеть
                  │
        ┌─────────▼──────────┐        ┌───────────────────────────┐
        │ домашний сервер    │        │ LAN-ПК с моделями         │
        │ 12 ядер / 16 ГБ    │        │  LLM  :1234  (LM Studio)  │
        │                    │        │  embeddings :1234         │
        │ docker compose:    │        └───────────▲───────────────┘
        │  app      :8000 ───┼────────────────────┘  HTTP по LAN
        │  postgres :5432    │
        │  qdrant   :6333    │
        └────────────────────┘
```

- `app` публикуется на хосте как `8000:8000`; доступ — `http://<ip>:8000`.
- `postgres` и `qdrant` наружу **не публикуются** (только внутренняя сеть
  compose).
- Caddy в текущей конфигурации **не используется** (нет домена). Профиль
  сохраняется в репозитории как заготовка на случай появления домена.
- Порт-форвардинг на роутере — опция, не требование: для приёмки достаточно
  доступа из локальной сети или через туннель; при CGNAT форвардинг невозможен.

## 4. Функциональные требования

### FR-1. Compose для прода (минимальный набор изменений)

1. `F-06`: заменить том `kb_data` на bind-mount:

```yaml
volumes: ["./data/kb:/data/kb"]
```

2. `restart: unless-stopped` для `postgres`, `qdrant`, `app` (одна строка,
   убирает «сайт не поднялся после перезагрузки сервера»).
3. Healthcheck `app` → `GET /health/live` (сервис `migrate` остаётся
   одноразовым).
4. Не публиковать порты `postgres`/`qdrant` (в текущем compose их нет);
   оставить `8000` только у `app`.
5. `COOKIE_SECURE=false` в прод-`.env` (HTTP, см. §7 «Риски»); при появлении
   TLS — вернуть `true`.
6. Caddy — профиль `prod`, запускается только при наличии домена:
   `docker compose --profile prod up -d`.

Ничего сверх этого не добавляем (DEV-03): без swarm, k8s, reverse-proxy
по умолчанию, лимитов памяти и сложных политик логирования.

### FR-2. Внешние зависимости: LLM и эмбеддинги в LAN

- `LLM_BASE_URL=http://<lan-ip>:1234/v1`, `EMBEDDING_BASE_URL=http://<lan-ip>:1234/v1`
  (база без `/embeddings`), ключи-заглушки допустимы для LM Studio.
- Модель эмбеддингов — **одна и та же** в dev и prod, мультиязычная (ru/en);
  кандидат — `text-embedding-qwen3-embedding-0.6b` (уже в `.env.example`).
  Смена модели требует `ingest.py --recreate-collection` (04 FR-8).
- Контейнер должен видеть LAN-адрес: проверка
  `docker compose exec app python -c "import httpx;print(httpx.get('http://<lan-ip>:1234/v1/models').status_code)"`.
  `host.docker.internal` работает только для моделей **на самом сервере** —
  для LAN-ПК указывается IP.
- Если LAN-ПК выключен: `/health` → `llm: down`, новый вопрос даёт
  `llm_unavailable` (03); чат и история продолжают работать.
- OpenRouter остаётся альтернативой: меняются `LLM_BASE_URL`/`LLM_API_KEY`/
  `LLM_MODEL` в `.env` без правки кода (02 PR-15).

### FR-3. Процедура деплоя

`scripts/deploy.sh` (идемпотентный, запускается на сервере):

```bash
#!/usr/bin/env bash
set -euo pipefail
git pull --ff-only
docker compose build app
docker compose run --rm migrate       # alembic upgrade head
docker compose up -d
for i in $(seq 1 30); do
  curl -fsS http://localhost:8000/health/live && exit 0
  sleep 2
done
echo "healthcheck failed" >&2; exit 1
```

- Простой на время рестарта допустим (один экземпляр, 1–2 пользователя).
- Откат: `git checkout <тег>` → повтор шагов сборки и `up -d`. Образы
  помечаются тегом коммита, чтобы откат не пересобирал «старый» код из кэша.
- Деплой не запускает `ingest.py` (04 FR-10) и eval: индексация и
  `run.py --http`/`report.py` — отдельные осознанные действия (08 OQ-08-01).
- Автодеплой по push и CI — бэклог.

### FR-4. Конфигурация и секреты на сервере

- `.env` лежит рядом с `docker-compose.yml`, права `600`, владелец — сервисный
  пользователь; `.env` в `.gitignore`.
- `.env.example` содержит только заглушки; реальные ключи не коммитятся
  (07 FR-10).
- `DEBUG=false`; `APP_VERSION` — тег/коммит, отображается в `/health`.
- Пароль администратора БД и `SUPPORT_EMAIL` — только в `.env`.
- `TZ` контейнера и `APP_TIMEZONE=Asia/Yekaterinburg` согласованы (06).

### FR-5. Наблюдаемость без инфраструктуры

- Логи — JSON в stdout (`structlog`), смотрим `docker compose logs -f app`.
- Ручная проверка после деплоя: `docker compose ps` + `/health` +
  `curl /health/live`.
- Опционально: внешний uptime-чек `/health` раз в 5 минут (бесплатный сервис
  или cron) — фиксируется как рекомендуемое, не обязательное.
- Метрик, дашбордов и алертов нет (DEV-03).

### FR-6. Восстановление после сбоя

- Перезагрузка сервера: контейнеры поднимаются сами (`unless-stopped`).
- Потеря данных PostgreSQL: восстановление из бэкапа — **бэклог** (DEV-04);
  до его реализации потеря чатов/аккаунтов считается принятым риском.
- Потеря Qdrant: `ingest.py` пересобирает индекс из `raw/` + манифеста.
- Потеря `data/kb/md/`: пересоздаётся конвертацией.
- Потеря `data/kb/raw/`: невосстановима — корпус дублируется вручную
  (архив/облако), это ответственность автора.

## 6. Граничные случаи

| Ситуация | Поведение |
|---|---|
| Нет домена | доступ по `http://<ip>:8000`, Caddy не запускается |
| CGNAT у провайдера | порт-форвардинг невозможен; демо в LAN или туннель |
| LAN-ПК с моделью выключен | `/health` → `llm: down`, новый вопрос → `llm_unavailable` |
| LAN-IP изменился (DHCP) | правка `.env` + рестарт; рекомендуется статическая аренда |
| Порт 8000 занят | `app` не стартует, healthcheck не проходит, `deploy.sh` код 1 |
| Миграция упала | `deploy.sh` останавливается до `up -d`, старая версия продолжает работать |
| Диск заполнен | ingest падает с `failed`, вопросы продолжают работать |
| Перезагрузка сервера | контейнеры поднимаются автоматически |
| Перезагрузка LAN-ПК | LLM недоступна до его возврата, история цела |
| Смена модели эмбеддингов | `--recreate-collection`, полный ingest |
| HTTPS без домена | не поддерживается; самоподписанный сертификат не используем |

## 7. Риски и ограничения (приняты осознанно)

1. **HTTP без TLS.** Пароль и сессионная cookie передаются открытым текстом.
   Приемлемо только для локальной сети/демо. При появлении домена — Caddy и
   `COOKIE_SECURE=true`. Для проверки из интернета рекомендуется туннель с TLS
   (Cloudflare Tunnel) — бэклог.
2. **Нет бэкапов.** Потеря PostgreSQL необратима для истории и аккаунтов
   (DEV-04).
3. **Единственный экземпляр.** Падение процесса = недоступность; автоперезапуск
   контейнера покрывает типичные случаи.
4. **Зависимость от домашней сети.** Отключение электричества/интернета
   останавливает демо; на приёмке проверяется заранее.
5. **Нет мониторинга.** О падении узнаём вручную или от пользователя.

- [ ] При выключенном LAN-ПК `/health` показывает `llm: down`, сервис не падает.
- [ ] Перезагрузка сервера восстанавливает работу без ручных действий.
