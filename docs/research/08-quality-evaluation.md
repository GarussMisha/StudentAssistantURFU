## 1. Контекст и цель

Качество ответов — главный измеримый результат проекта (00, критерий 2). При этом
«качество» здесь — не метрика эмбеддингов, а **человеческое суждение**: ответ
верен по существу, опирается на реальный фрагмент корпуса и не выдумывает.

Поэтому процесс строится вокруг ручной оценки (QA-01):
**пул вопросов → датасет → автоматический сбор ответов → ручная проверка →
отчёт и пороги.** Автоматика отвечает только за формальную часть (статус,
источники, отсутствие сбоев) и за то, чтобы проверяющему было удобно.

## 3. Процесс

```
пул кандидатов (60+) ──курирование──► dataset.yaml (40)
        │                                   │
        │                          run.py (in-process)
        │                                   ▼
        │                    runs/<ts>/answers.json + worksheet.md
        │                                   │
        │                          ручная оценка (человек)
        │                                   ▼
        │                    runs/<ts>/scores.yaml (0/1/2)
        │                                   │
        └──────────────► report.py ──► report.md + exit code
```

Роли: автор корпуса курирует вопросы и ставит оценки; runner и report — скрипты.

## 4. Функциональные требования

### FR-1. Пул вопросов и датасет

- Сначала автор формирует **пул кандидатов** (`eval/candidates.yaml`, 60+
  вопросов, по 3–4 на документ). Пул не участвует в приёмке и может расти.
- Из пула курируется `eval/dataset.yaml`:

```yaml
version: 1
corpus_content_hash: "…"        # фиксируется на момент курирования
questions:
  - id: g01
    subset: grounded
    question: "Какие роли выделяет Scrum?"
    expected_documents: [01_scrum_agile_guide]
    expected_heading: "Scrum Guide > Роли"
    reference_answer: "Product Owner, Scrum Master, Developers…"
    key_facts: ["Product Owner", "Scrum Master", "Developers"]
    notes: "Ответ полностью в одном разделе"
  - id: u01
    subset: ungrounded
    question: "Как настроить Kubernetes Ingress?"
    expected_documents: []
    key_facts: ["Ingress-контроллер"]
    notes: "Вне корпуса: PM/Agile/ГОСТы"
```

- Правила курирования:
  - 20 grounded — ответ есть в корпусе, желательно в одном документе;
  - 20 ungrounded — тема вне корпуса (инфраструктура, код, личные вопросы);
  - покрытие: минимум **60%** документов корпуса и минимум **2** вопроса на
    каждый `material_type`;
  - вопросы не дублируют примеры со стартового экрана (01 UI-06);
  - формулировки разные по типу: определение, «как», «чем отличается»,
    «что делать, если».
- Multi-turn — отдельный файл `eval/multi_turn.yaml`, 5 диалогов по 3 реплики
  (уточнение, местоимение, смена темы).

### FR-2. Автоматический прогон

`uv run python eval/run.py [--dataset eval/dataset.yaml] [--only g01,g02]
[--repeat N] [--http <url>]`

- Основной режим — **in-process**: вызов `RagResult` (05) без HTTP/SSE, чтобы
  прогон был быстрым, детерминированным и не зависел от веб-слоя.
- Для каждого вопроса сохраняется: `status`, `content_md`, `sources`,
  `meta` (attempts, top_score, tokens_in, duration_ms, model), время.
- Артефакты прогона: `eval/runs/<YYYY-MM-DD_HHMM>/answers.json` (машинный) и
  `worksheet.md` — человекочитаемая таблица: вопрос, ответ, источники,
  ожидаемые документы, пустая колонка «Оценка» и «Комментарий».
- `--http` — smoke-прогон 5 вопросов против развёрнутого сервиса (проверка SSE
  и деплоя). В порогах не участвует.
- `--repeat N` — повторные прогоны для оценки стабильности; в отчёт идёт
  первый, различия фиксируются отдельно.
- Сбой одного вопроса (`no_reply`, `error`) не останавливает прогон; он
  помечается и делает прогон недействительным для приёмки (QA-04, п.4).

### FR-3. Ручная оценка

- Человек открывает `worksheet.md`, сверяет ответ с `key_facts` и источниками,
  заполняет `eval/runs/<ts>/scores.yaml`:

```yaml
scores:
  g01: {value: 2, comment: "Все три роли, источник верный"}
  g05: {value: 1, comment: "Верно, но сослался на другой документ"}
```

- Шкала:
  - **2** — ответ верен, все `key_facts` присутствуют, источники соответствуют;
  - **1** — частично верно, либо верно, но источник не тот / неполный;
  - **0** — неверно, выдумано, противоречит корпусу.
- Оценивается **каждый** вопрос: пропуск оценки = прогон не принят.
- Для ungrounded дополнительно проверяется: нет ссылок на источники и нет
  утверждений вида «согласно базе знаний».
- Для grounded: хотя бы один источник должен **семантически подтверждать**
  ключевой факт (не «похожий документ»); иначе — максимум 1 и пометка
  `citation_semantic_miss`.

### FR-4. Автоматические проверки

Runner сам считает формальные признаки и кладёт их в `answers.json`:

| Проверка | Правило |
|---|---|
| `status_match` | статус совпал с ожидаемым (`grounded` для g*, `ungrounded` для u*) |
| `sources_resolvable` | каждый `source_no` → существующий чанк из контекста, `snippet` непуст |
| `expected_doc_hit` | `expected_documents ⊆ {document_title источников}` (для grounded) |
| `no_links_in_ungrounded` | у ungrounded `sources == []` |
| `no_failure` | статус не `no_reply`/`error` |

Автоматика **не** выставляет 0/1/2 и не заменяет человека (QA-01).

### FR-5. Вердикт по вопросу и пороги

Проход grounded-вопроса = `status_match` **и** `expected_doc_hit` **и**
`sources_resolvable` **и** ручная оценка **2**.

Проход ungrounded-вопроса = `status_match` **и** `no_links_in_ungrounded` **и**
ручная оценка **≥ 1**.

Проход multi-turn-диалога = последний ответ учитывает контекст (ручная оценка
2) и не теряет источник, если он ожидается.

Пороги приёмки (QA-04):

| Метрика | Порог |
|---|---|
| grounded_pass | ≥ **19/20** (95%) |
| ungrounded_pass | ≥ **16/20** (80%) |
| citation_validity | **100%** (`sources_resolvable` на всех ответах) |
| failures | **0** (`no_reply`/`error`) |
| multi_turn_pass | ≥ **4/5** |

Порог «80% двоек» и «4/5 отказов» из README **отменяются** (дельты D-29,
D-30): отказ заменён режимом `ungrounded` (02 D-02), а «двойки» уже входят в
`grounded_pass`.

### FR-6. Отчёт

`uv run python eval/report.py --run <ts>` — склеивает `answers.json` +
`scores.yaml`, проверяет полноту оценок, формирует `eval/report.md` и
`eval/runs/<ts>/report.json`.

Обязательные поля отчёта:

- дата и время, commit, `corpus_content_hash`;
- модель LLM, модель эмбеддингов, `RETRIEVAL_SCORE_THRESHOLD`, `temperature`,
  `max_tokens`;
- таблица по вопросам: id, вопрос, статус, источники, оценка, комментарий,
  автоматические флаги;
- агрегаты и вердикт «принято/не принято» с указанием не пройденных порогов;
- распределение оценок 0/1/2 и список `citation_semantic_miss`.

`report.py` завершается кодом 0 только при выполнении всех порогов, иначе 1 —
это и есть машиночитаемая приёмка для CI/скрипта деплоя.

### FR-7. Воспроизводимость

- В отчёте фиксируются все параметры генерации и retrieval; при изменении
  модели, порога или корпуса отчёт помечается «не сравним с предыдущим»,
  если `corpus_content_hash`/модель отличаются.
- `temperature=0.2` делает прогон приблизительно стабильным; `--repeat 2`
  позволяет увидеть разброс, но не входит в пороги.
- Датасет и `candidates.yaml` — в git; `runs/` — вне git (артефакты), в git
  попадает только `report.md`.

## 6. Граничные случаи

| Ситуация | Поведение |
|---|---|
| Вопрос без документа в корпусе | исключается при курировании; после ingest проверяется автоматически |
| Документ переименован | `expected_documents` использует `doc_key`, не имя файла |
| Корпус изменился после курирования | отчёт помечает несовпадение hash, требуется ревизия датасета |
| Модель вернула `no_answer` на grounded-вопрос | вопрос не пройден, попадает в failures/агрегат |
| Ungrounded-вопрос дал `grounded` с чужой цитатой | провал `status_match` + семантический мисс |
| Не все вопросы оценены | `report.py` отказывается строить отчёт, код 2 |
| Нет `scores.yaml` | то же |
| Один вопрос упал с `error` | прогон помечен недействительным, отчёт строится с пометкой |
| Пустой датасет | код 2 |
| Повторный прогон в тот же день | каталог с суффиксом `_2`, история сохраняется |

## 7. НФТ

- **Время прогона:** 40 вопросов in-process ≤ 15 мин на целевой модели;
  smoke `--http` — ≤ 3 мин.
- **Прозрачность:** worksheet читается без инструментов (Markdown + таблицы).
- **Воспроизводимость:** все параметры и хеш корпуса в отчёте.
- **Честность:** автоматика не выставляет содержательные оценки; ручные
  комментарии сохраняются дословно.
- **Приватность:** в датасете только синтетические/обезличенные вопросы, без
  реальных чатов студентов (02 FR-9).
