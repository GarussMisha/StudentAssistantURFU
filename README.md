# ИИ-ассистент по проектной деятельности

## Описание проекта

ИИ-ассистент для студентов на основе **RAG-архитектуры** (Retrieval-Augmented Generation). Помогает студентам при выполнении проектной деятельности: консультирует по вопросам управления проектами, Agile, Scrum, DevOps и другим инженерным практикам.

В отличие от обычных LLM-чатов ассистент отвечает **по проиндексированной базе знаний** (статьи, книги, ГОСТы, методические материалы): каждый ответ по базе подкрепляется цитатой из источника. Если подтверждённого ответа в базе нет, ассистент отвечает из общих знаний модели, но **явно предупреждает** об этом и не выдаёт такой ответ за цитату.

Ключевые принципы продукта:

- **Always-retrieve** — перед любым ответом выполняется поиск по базе; генерация без retrieval исключена.
- **Цитаты и источники** — ответ по базе ссылается на реально использованные фрагменты (документ, тип материала, раздел, текст); неиспользованные чанки в источники не попадают.
- **Честное предупреждение** — если релевантного фрагмента нет, ответ помечается как не основанный на базе знаний и не содержит ссылок.
- **Измеримое качество** — ручная оценка на датасете 20 + 20 вопросов и 5 multi-turn диалогов, отчёт с порогами приёмки.

## Возможности

Возможности описаны как capabilities в OpenSpec (см. [Подход: OpenSpec](#подход-openspec)):

| Capability | Что даёт |
|---|---|
| `knowledge-base` | Приём корпуса, конвертация PDF/DOCX/MD в Markdown, чанкинг по заголовкам, индексация в Qdrant, статусы обработки |
| `rag-answering` | Ответы по базе: retrieval, переформулировка запроса в multi-turn, цитаты, предупреждение при отсутствии подтверждения |
| `conversation-history` | Чаты, сообщения, ленивая загрузка истории, владение диалогом, оценка ответа «полезно / неполезно» |
| `user-accounts` | Регистрация по email и паролю (Argon2id), вход/выход, серверные сессии |
| `web-interface` | Страницы чата, истории, источников и регистрации; состояния загрузки, ошибки и пустой базы знаний |
| `quality-evaluation` | Датасет 20 + 20 вопросов и 5 multi-turn диалогов, ручная оценка, прогон и отчёт |

## Технологический стек

- **Backend:** Python 3.14, FastAPI, uvicorn
- **База данных:** PostgreSQL (SQLAlchemy async + Alembic) — источник истины: пользователи, сессии, диалоги, документы, статусы
- **Векторное хранилище:** Qdrant — производный индекс эмбеддингов чанков
- **LLM и эмбеддинги:** OpenAI-совместимый протокол через LangChain; LM Studio в локальной сети (в том числе на другом ПК) или OpenRouter — переключение только через `.env`
- **Сбор документации:** markitdown + pymupdf4llm (PDF, DOCX → Markdown), таблицы — в HTML
- **Веб-интерфейс:** Jinja2 + HTMX + SSE (серверный рендеринг без SPA)
- **Безопасность:** Argon2id, HttpOnly-cookie, CSRF, защита входа от перебора
- **Контейнеризация:** Docker + Docker Compose (+ Caddy как необязательный профиль при наличии домена)

## Архитектура

### Пайплайн RAG

```
data/kb/raw (PDF/DOCX/MD)
        │  конвертация → канонический Markdown (data/kb/md)
        ▼
   чанкинг по заголовкам (heading_path, склейка коротких секций,
   дробление длинных с перекрытием ~15%, таблицы неделимые)
        │  эмбеддинги (OpenAI-совместимый шлюз)
        ▼
   Qdrant (векторы + payload: текст, документ, heading_path, путь)

Вопрос пользователя
        │  переформулировка запроса (последние 3 сообщения)
        ▼
   retrieval top-10 в Qdrant → фильтр по порогу релевантности (0.65)
        │  пусто/ниже порога → ответ без БЗ (ungrounded) с предупреждением
        ▼
   генерация ответа «только по контексту» + цитаты из найденных чанков
```

### Хранение данных

- **PostgreSQL** — источник истины: пользователи, серверные сессии, чаты, сообщения, цитаты, оценки, документы и статусы индексации. Транзакции и реляционные связи здесь.
- **Qdrant** — производный векторный индекс. Текст чанка дублируется в payload для цитат; исходный Markdown хранится в `data/kb/md/`.

### LLM-шлюз

Один OpenAI-совместимый интерфейс для chat completions и embeddings. Настройки `LLM_*` и `EMBEDDING_*` раздельные: провайдер, URL, ключ и модель меняются в `.env` без правки кода. В разработке — локальная LM Studio (LLM и эмбеддинги могут быть на другом ПК в локальной сети), в продакшене — та же схема или OpenRouter.

### Веб-слой

Серверный рендеринг страниц на Jinja2, частичные обновления через HTMX, потоковая выдача ответа через SSE. Отдельной сборки фронтенда нет.

Полное обоснование решений (always-retrieve, чанкинг по заголовкам, Markdown как канонический формат, PostgreSQL + Qdrant, серверные сессии, оценка качества) — в `design.md` активного изменения (`openspec/changes/`).

## Подход: OpenSpec

Разработка ведётся **spec-driven** через [OpenSpec](https://github.com/Fission-AI/OpenSpec) (схема `spec-driven`). Спецификации — источник истины о том, что сервис должен уметь; код реализует их.

### Структура `openspec/`

```
openspec/
├── config.yaml          # схема и правила артефактов
├── specs/               # основные (активные) спецификации — результат приёмки изменений
└── changes/             # активные изменения: proposal.md, design.md, tasks.md
                         # и дельты спецификаций по capabilities
```

### Жизненный цикл change

Каждое изменение проходит путь: **proposal → design → specs → tasks → реализация → архивирование**. Артефакты валидируются командой:

```bash
openspec validate "<имя-изменения>" --strict
```

После реализации и приёмки change переносится в архив, а его дельты сливаются в основные спецификации `openspec/specs/`. Активные изменения всегда лежат в каталоге `openspec/changes/`.

### План реализации

Реализация идёт **вертикальными срезами M0–M5** (рискованные места проверяются первыми):

| Срез | Содержание |
|---|---|
| **M0** | 3 пилотных файла: конвертация, чанкинг, эмбеддинги, retrieval; ответ с цитатой |
| **M1** | 10 документов, retrieval, порог релевантности, 10+3 вопроса в smoke-проверке |
| **M2** | Веб-чат, история, карточка источника |
| **M3** | Auth, ленивая история, оценка ответа |
| **M4** | Датасет 20 + 20 и 5 multi-turn, eval-отчёт, деплой (домашний сервер, HTTP по IP) |
| **M5** | Админка, повторная индексация, полировка |

Актуальный статус реализации (чекбоксы по задачам) — в `tasks.md` активного изменения в каталоге `openspec/changes/`. Код пока не написан — см. [раздел «Запуск»](#запуск).

## Запуск

> ⚠️ **В разработке.** Сервис ещё не реализован — раздел заполняется по мере выполнения задач M0–M5. Ниже — целевой сценарий запуска, команды заработают после соответствующих задач.

### Требования

- Docker и Docker Compose
- Python 3.14 + [uv](https://docs.astral.sh/uv/) (для локальной разработки без Docker)
- LLM и эмбеддинги: OpenAI-совместимый API (LM Studio в локальной сети или OpenRouter)

### Запуск через Docker Compose

```bash
# 1. Настроить окружение
cp .env.example .env
#    отредактируйте .env: LLM_BASE_URL / EMBEDDING_BASE_URL, ключи, БД

# 2. Подготовить базу знаний в data/kb/raw/ (PDF/DOCX/MD) и manifest.yaml
#    каталог монтируется в контейнер (bind-mount), файлы видны приложению

# 3. Собрать образы, применить миграции и запустить
docker compose up -d

# 4. Индексировать корпус (CLI)
uv run python scripts/ingest.py
```

После запуска: приложение на `http://localhost:8000`, health-check — `GET /health`.
Доступ снаружи — `http://<ip>:8000`; HTTPS появится только после подключения
домена (см. ниже).

### Обновление стенда

```bash
./scripts/deploy.sh    # git pull → build → миграции → up -d → healthcheck
```

Откат — `git checkout <тег>` и повторный запуск скрипта.

### Локальная разработка (без Docker)

```bash
uv sync                                  # зависимости
cp .env.example .env                     # окружение
uv run alembic upgrade head              # миграции БД
uv run uvicorn app.main:app --reload     # запуск приложения
```

Полный список переменных окружения — в [`.env.example`](.env.example).

### Ограничения текущего стенда

- **HTTPS не используется**: домена нет, приложение доступно по IP. Пароли и
  сессионная cookie передаются открытым текстом — это допустимо только для
  локальной сети и демонстрации. При появлении домена включается профиль
  `prod` с Caddy и `COOKIE_SECURE=true`.
- **Бэкапы PostgreSQL не настроены** — история и аккаунты невосстановимы при
  потере БД.
- LLM и эмбеддинги зависят от доступности ПК с моделями в локальной сети.
- Один экземпляр приложения, без мониторинга и алертов.

## Оценка качества

Качество ответов — first-class артефакт проекта (capability `quality-evaluation`):

- **Датасет:** 20 вопросов, ответ на которые есть в корпусе (grounded), 20 вопросов вне корпуса (ungrounded) и 5 multi-turn диалогов по 3 реплики.
- **Шкала:** ручная оценка 0 / 1 / 2 с комментарием (2 — верно и источник подтверждает; 1 — частично или не тот источник; 0 — неверно/выдумано).
- **Пороги приёмки:** ≥ 19/20 grounded, ≥ 16/20 ungrounded, 100% валидность цитирования, 0 сбоев, ≥ 4/5 multi-turn.
- **Отчёт:** `eval/report.md` (дата, конфигурация, метрики, таблица по каждому вопросу) и сохранённые прогоны в `eval/runs/`.

## Критерии приёмки

1. Развёрнут и доступен для тестирования ИИ-ассистент (HTTP по IP; HTTPS — после появления домена).
2. Качество ответов оценено на датасете 20 + 20 вопросов и 5 multi-turn диалогов — отчёт не ниже порогов приёмки.
3. Кодовая база и база знаний задокументированы.
