# ИИ-ассистент по проектной деятельности

## Описание проекта

ИИ-ассистент для студентов на основе **RAG-архитектуры** (Retrieval-Augmented Generation). Помогает студентам при выполнении проектной деятельности: консультирует по вопросам управления проектами, Agile, Scrum, DevOps и другим инженерным практикам.

В отличие от обычных LLM-чатов ассистент сначала ищет ответ в проиндексированной базе знаний (статьи, книги, ГОСТы, методички УРФУ) и отвечает **с цитатами из найденных фрагментов**. Если ответа в базе нет, он не выдаёт выдумку за факт: предупреждает, что отвечает из общих знаний модели.

Ключевые принципы продукта (по `docs/research/02-product-and-users.md`):

- **Retrieval перед ответом** — любой ответ начинается с поиска по базе; генерация «из головы» без retrieval исключена.
- **Три режима ответа** — `grounded` (ответ по базе, обязательны цитаты), `ungrounded` (в базе достаточного ответа нет → предупреждение + общие знания модели, без цитат), `no_answer` (модель не дала содержательного ответа). Ошибки сервиса — отдельный режим `error`.
- **Цитаты и источники** — валидность цитирования 100%: каждый маркер `[1]…[n]` ведёт на реально использованный фрагмент (документ, тип материала, раздел, текст).
- **Измеримое качество** — eval-датасет из двух подмножеств по 20 вопросов и пороги ≥ 19/20 и ≥ 16/20.

## Возможности

Возможности фиксируются как capabilities (спецификации в `openspec/specs/` появятся вместе с первыми изменениями, см. [Подход: OpenSpec](#подход-openspec)):

| Capability | Что даёт |
|---|---|
| `knowledge-base` | Приём корпуса 20–40 документов, манифест, конвертация PDF/DOCX/MD в Markdown, чанкинг по заголовкам, индексация в Qdrant, статусы обработки |
| `rag-answering` | Retrieval перед ответом, переформулировка запроса в multi-turn, цитаты, режимы `grounded` / `ungrounded` / `no_answer` |
| `conversation-history` | Чаты и сообщения в PostgreSQL, оценка ответа (лайк/дизлайк + комментарий), удаление всей истории; поиск, переименование и удаление отдельного чата — бэклог |
| `user-accounts` | Только авторизованный доступ: регистрация email + пароль + согласие с правилами и обработкой ПДн, вход/выход, серверные сессии |
| `web-interface` | Страницы чата, истории, источников и регистрации; состояния загрузки, ошибки и пустой базы знаний |
| `quality-evaluation` | Eval-датасет 20 + 20 вопросов, прогон пайплайна, отчёт и пороги приёмки |

Контракт между этими частями (модель данных, HTTP API, SSE, статусы, `/health`) фиксирует исследование `docs/research/03-cross-cutting-contracts.md`.

## Технологический стек

- **Backend:** Python 3.14, FastAPI, uvicorn
- **База данных:** PostgreSQL (SQLAlchemy async + Alembic) — источник истины для данных: пользователи, сессии, диалоги, документы, статусы
- **Векторное хранилище:** Qdrant — производный индекс эмбеддингов чанков
- **LLM и эмбеддинги:** OpenAI-совместимый протокол через LangChain (в разработке — локальная LM Studio, в продакшене — OpenRouter; замена только переменными окружения)
- **Ограничение нагрузки на LLM:** очередь в процессе приложения — 4 слота, буфер ожидания 8, ожидание ≤ 60 с; переполнение → `503 llm_busy`
- **Сбор документации:** markitdown + pymupdf4llm (PDF, DOCX → Markdown)
- **Веб-интерфейс:** Jinja2 + HTMX + SSE (серверный рендеринг без SPA)
- **Безопасность:** Argon2 для паролей, HttpOnly/SameSite-cookie, CSRF во всех изменяющих запросах; из ПДн — только email
- **Контейнеризация:** Docker + Docker Compose (+ Caddy для HTTPS в prod-профиле)

## Архитектура

### Пайплайн RAG

```
data/kb/raw (PDF/DOCX/MD)
        │  конвертация → канонический Markdown
        ▼
   чанкинг по заголовкам (heading_path, склейка коротких секций,
   дробление длинных с перекрытием ~15%, таблицы неделимые)
        │  эмбеддинги (OpenAI-совместимый шлюз)
        ▼
   Qdrant (векторы + payload: текст, документ, heading_path, путь)

Вопрос пользователя
        │  переформулировка запроса (последние 3–5 сообщений)
        ▼
   retrieval top-k в Qdrant → порог релевантности + проверка цитат
        │  есть валидные фрагменты → grounded (+ цитаты [1]…[n])
        │  нет → ungrounded: предупреждение, ответ из общих знаний, sources: []
        ▼
   стрим ответа по SSE: meta → delta* → sources → done {status}
```

### Хранение данных

- **PostgreSQL** — источник истины: пользователи, серверные сессии, чаты, сообщения, цитаты (со снимком метаданных), оценки, документы и статусы индексации. Транзакции и реляционные связи здесь.
- **Qdrant** — производный векторный индекс. Текст чанка дублируется в payload для цитат; канонический Markdown хранится в `data/kb/md/`. При расхождении индекс перестраивается, а не «чинится» по векторам.

### LLM-шлюз

Один OpenAI-совместимый интерфейс для chat completions и embeddings: `LLM_BASE_URL` / `EMBEDDING_BASE_URL` (оба — база `…/v1`, без `/embeddings`), ключи, имена моделей. Ветвление по провайдеру в коде запрещено; локальная модель ↔ облачная меняются только `.env`. Эмбеддинги по умолчанию локальные.

### Веб-слой

Серверный рендеринг страниц на Jinja2, частичные обновления через HTMX, потоковая выдача ответа через SSE (`meta`, `delta`, `sources`, `done`, `error`). Отдельной сборки фронтенда нет. JSON API живёт под `/api` без версии; изменяющие запросы требуют CSRF-токен.

### Документация и источник истины

| Где | Что |
|---|---|
| `docs/00-project-task.md` | исходная постановка задачи |
| `docs/research/` | исследования требований — **источник истины** о том, что сервис должен уметь (01 — веб-интерфейс, 02 — продукт и пользователи, 03 — сквозные контракты) |
| `openspec/` | спецификации и изменения: они пишутся по исследованиям, код реализует их |

Обоснование технических решений (чанкинг по заголовкам, Markdown как канонический формат, PostgreSQL + Qdrant, серверные сессии, контракты API) — в соответствующих разделах исследований и в `design.md` активного изменения.

## Подход: OpenSpec

Разработка ведётся **spec-driven** через [OpenSpec](https://github.com/Fission-AI/OpenSpec) (схема `spec-driven`). Требования берутся из исследований `docs/research/` — они источник истины; спецификации в `openspec/specs/` описывают поведение сервиса по этим исследованиям, а код реализует спецификации.

### Структура `openspec/`

```
openspec/
├── config.yaml          # схема и правила артефактов
├── specs/               # основные (активные) спецификации — результат приёмки изменений
└── changes/             # активные изменения: proposal.md, design.md, tasks.md
                         # и дельты спецификаций по capabilities
```

### Жизненный цикл change

Каждое изменение проходит путь: **proposal → design → specs → tasks → реализация → архивирование**. Артефакты валидируются командой:

```bash
openspec validate "<имя-изменения>" --strict
```

После реализации и приёмки change переносится в архив, а его дельты сливаются в основные спецификации `openspec/specs/`. Активные изменения всегда лежат в каталоге `openspec/changes/`.

### План реализации

Реализация идёт **вертикальными срезами M0–M5** (рискованные места проверяются первыми):

| Срез | Содержание |
|---|---|
| **M0** | 3 пилотных файла: конвертация, чанкинг, эмбеддинги, retrieval; ответ с цитатой |
| **M1** | 10 документов, retrieval, порог релевантности и режимы `grounded` / `ungrounded`, smoke-проверка на подмножестве eval-вопросов |
| **M2** | Веб-чат, история, карточка источника |
| **M3** | Auth, профиль, оценка ответа |
| **M4** | Eval-датасет 20 + 20 вопросов, eval-отчёт, деплой на VPS + HTTPS |
| **M5** | Админка, повторная индексация, полировка |

Актуальный статус реализации (чекбоксы по задачам) — в `tasks.md` активного изменения в каталоге `openspec/changes/`. Код пока не написан — см. [раздел «Запуск»](#запуск).

## Запуск

> ⚠️ **В разработке.** Сервис ещё не реализован — раздел заполняется по мере выполнения задач M0–M5. Ниже — целевой сценарий запуска, команды заработают после соответствующих задач.

### Требования

- Docker и Docker Compose
- Python 3.14 + [uv](https://docs.astral.sh/uv/) (для локальной разработки без Docker)
- LLM и эмбеддинги: OpenAI-совместимый API (локально — LM Studio, в продакшене — OpenRouter)

### Запуск через Docker Compose

```bash
# 1. Настроить окружение
cp .env.example .env
#    отредактируйте .env: LLM_BASE_URL / EMBEDDING_BASE_URL, ключи, БД

# 2. Положить исходники корпуса в data/kb/raw/ (PDF/DOCX/MD) и описать его в data/kb/manifest.yaml

# 3. Собрать образы, применить миграции и запустить
docker compose up -d

# 4. Индексировать корпус (CLI)
uv run python scripts/ingest.py
```

После запуска: приложение на `http://localhost:8000`; health-checkи — `GET /health/live` (для compose) и `GET /health` (состояние БД, Qdrant, LLM и базы знаний).

### Локальная разработка (без Docker)

```bash
uv sync                                  # зависимости
cp .env.example .env                     # окружение
uv run alembic upgrade head              # миграции БД
uv run uvicorn app.main:app --reload     # запуск приложения
```

Набор и значения по умолчанию переменных окружения зафиксированы в `docs/research/03-cross-cutting-contracts.md` (§5.4); `.env.example` синхронизируется с ним отдельной задачей.

## Оценка качества

Качество ответов — first-class артефакт проекта (capability `quality-evaluation`, метрики PR-10 и PR-14):

- **Датасет:** два подмножества по 20 вопросов — grounded («ответ есть в корпусе») и ungrounded («вопрос вне корпуса»). Состав фиксируется заранее, для каждого вопроса указывается ожидаемый режим ответа.
- **Метрики и пороги приёмки:** ≥ 19/20 правильных ответов по базе (95%), ≥ 16/20 корректных ответов без базы (80%), 100% валидность цитирования.
- **Шкала оценки, генерация и прогон** — фиксирует исследование `08-quality-evaluation.md` (открытый вопрос OQ-06).
- **Отчёт:** `eval/report.md` (дата, конфигурация, метрики, таблица по каждому вопросу).

## Критерии приёмки

1. Сервис развёрнут и доступен для тестирования по HTTPS; критический путь проходит без ручных действий администратора: открыть сайт → зарегистрироваться → новый чат → задать вопрос → получить ответ с цитатами.
2. Отчёт `eval/report.md` не ниже порогов: ≥ 19/20 grounded, ≥ 16/20 ungrounded, валидность цитат 100%.
3. Кодовая база и база знаний задокументированы (`docs/research/`, спецификации `openspec/`, README).
