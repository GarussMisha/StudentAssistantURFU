# Spec Delta

## Purpose

Формирует проверяемую базу знаний из исходных учебных материалов: принимает документы, приводит их к единому виду, разбивает на цитируемые фрагменты и поддерживает актуальный индекс с понятными статусами обработки.

## ADDED Requirements

### Requirement: Манифест корпуса

Система SHALL вести манифест корпуса, в котором каждый документ описан идентификатором, названием, типом материала, путём к исходному файлу и статусом обработки. Манифест SHALL быть единственным источником состава индекса. Новый поддерживаемый файл SHALL добавляться в манифест, а запись без файла SHALL помечаться ошибкой с причиной.

#### Scenario: Новый документ попадает в манифест

- **WHEN** в каталоге корпуса появляется новый поддерживаемый файл
- **THEN** система добавляет его в манифест со статусом `pending` и уникальным идентификатором

#### Scenario: Файл из манифеста отсутствует

- **WHEN** файл, указанный в манифесте, отсутствует на диске
- **THEN** запись получает статус `failed` с причиной «файл не найден», а обработка остальных документов продолжается

#### Scenario: Повторный запуск не создаёт дубликат

- **WHEN** повторный запуск обнаруживает уже известный файл
- **THEN** дубликат записи в манифесте не создаётся

### Requirement: Поддерживаемые форматы и отказ от сканов

Система SHALL принимать Markdown, DOCX и PDF с текстовым слоем. Файл другого формата SHALL получать статус `failed` с причиной «формат не поддерживается» и не попадать в индекс. PDF без извлекаемого текста или с объёмом текста ниже настроенного порога SHALL также получать статус `failed`; OCR в первой версии не выполняется.

#### Scenario: Поддерживаемый формат допускается к обработке

- **WHEN** документ имеет формат Markdown, DOCX или PDF с текстовым слоем
- **THEN** он допускается к конвертации и чанкингу

#### Scenario: Неподдерживаемый формат не ломает обработку

- **WHEN** в корпусе встречается файл неподдерживаемого формата
- **THEN** он получает статус `failed` с причиной, а остальные документы обрабатываются

#### Scenario: Скан без текстового слоя отклоняется

- **WHEN** PDF не содержит извлекаемого текстового слоя
- **THEN** документ получает статус `failed` с причиной «нет текстового слоя», и чанки для него не создаются

### Requirement: Конвертация в канонический Markdown

DOCX и PDF SHALL конвертироваться в Markdown один раз. Результат SHALL сохраняться как обработанная копия, а исходный файл SHALL оставаться неизменным. Markdown-документы SHALL проходить нормализацию без повторной конвертации. Ошибка конвертации SHALL переводить документ в `failed` с причиной, не удаляя исходник.

#### Scenario: Успешная конвертация сохраняет обе версии

- **WHEN** DOCX или PDF успешно конвертирован
- **THEN** обработанный Markdown сохраняется, а исходный файл остаётся доступен

#### Scenario: Ошибка конвертации не удаляет исходник

- **WHEN** конвертация завершается ошибкой
- **THEN** документ получает статус `failed` с причиной, а исходный файл сохраняется

#### Scenario: Markdown не конвертируется повторно

- **WHEN** исходный документ уже представлен в Markdown
- **THEN** повторная конвертация не выполняется, выполняется только нормализация

### Requirement: Таблицы сохраняют структуру

Таблицы из DOCX и PDF SHALL представляться в каноническом Markdown как HTML-таблицы с заголовком и строками. Чанкер SHALL рассматривать таблицу как неделимый блок: при дроблении длинной таблицы разрыв допускается только между строками, а заголовок SHALL повторяться в каждом фрагменте. Разрыв внутри строки или ячейки SHALL быть невозможен.

#### Scenario: Таблица превращается в HTML-блок

- **WHEN** документ содержит таблицу
- **THEN** в обработанном Markdown она представлена HTML-блоком с заголовком и строками

#### Scenario: Длинная таблица делится по строкам

- **WHEN** таблица превышает лимит размера чанка
- **THEN** она делится только между строками, и каждый фрагмент содержит повторённый заголовок

#### Scenario: Короткая таблица остаётся целой

- **WHEN** таблица умещается в лимит чанка
- **THEN** она целиком входит в один чанк

### Requirement: Чанкинг по заголовкам

Система SHALL разбивать документ по заголовкам, определяя верхний уровень заголовков в каждом документе и строя `heading_path` относительно него. Слишком короткие соседние секции SHALL склеиваться, а длинные SHALL дробиться до лимита токенов с перекрытием около 15%. Каждый чанк SHALL содержать `heading_path` и непустой текст.

#### Scenario: Разные уровни заголовков нормализуются

- **WHEN** в DOCX разделы размечены H1, а в Markdown — H2
- **THEN** `heading_path` обоих документов строится от их верхнего уровня и не содержит пустых сегментов

#### Scenario: Короткие секции склеиваются

- **WHEN** соседние секции короче минимального размера
- **THEN** они объединяются в один чанк

#### Scenario: Длинная секция дробится с перекрытием

- **WHEN** секция превышает лимит токенов
- **THEN** она дробится на несколько чанков с перекрытием около 15%

#### Scenario: Документ без заголовков

- **WHEN** документ не содержит заголовков
- **THEN** весь его текст обрабатывается как одна корневая секция

### Requirement: Индексация чанков

Для каждого чанка система SHALL вычислять эмбеддинг и сохранять вектор вместе с payload: текст чанка, идентификатор и название документа, тип материала, `heading_path` и путь к источнику. В индекс SHALL попадать только чанки документов со статусом `indexed`. Повторная индексация документа SHALL заменять его прежние векторы, не создавая дубликатов.

#### Scenario: Чанки получают векторы и метаданные

- **WHEN** документ успешно обработан
- **THEN** все его чанки получают векторы и payload с обязательными полями

#### Scenario: Повторная индексация заменяет старые векторы

- **WHEN** документ индексируется повторно
- **THEN** старые векторы этого документа заменяются, а дубликаты не появляются

#### Scenario: Ошибка эмбеддинга не даёт частичный индекс

- **WHEN** вычисление эмбеддинга завершается ошибкой
- **THEN** документ получает статус `failed`, а его неполный набор векторов не считается проиндексированным

### Requirement: Статусы обработки и сводка

Каждый документ SHALL находиться ровно в одном статусе: `pending`, `processing`, `indexed` или `failed`. Для `failed` SHALL храниться причина; для `indexed` — время последней успешной индексации. Система SHALL предоставлять сводку с количеством документов и чанков по статусам и датой последней успешной индексации.

#### Scenario: Успешная обработка меняет статусы последовательно

- **WHEN** документ проходит обработку
- **THEN** его статус последовательно меняется `pending` → `processing` → `indexed`

#### Scenario: Ошибка фиксируется в статусе

- **WHEN** обработка документа завершается ошибкой
- **THEN** статус становится `failed`, а причина доступна в сводке

#### Scenario: Сводка отражает состояние базы

- **WHEN** запрошена сводка базы знаний
- **THEN** она содержит количество документов и чанков по статусам и дату последней успешной индексации

### Requirement: Повторная индексация корпуса

Система SHALL поддерживать явную полную переиндексацию корпуса. Переиндексация SHALL обрабатывать все документы манифеста, сообщать итог по каждому документу и не смешивать чанки старой и новой версии одного документа. Изменение файла в корпусе SHALL обнаруживаться при следующей переиндексации.

#### Scenario: Полная переиндексация отчитывается по каждому документу

- **WHEN** запущена полная переиндексация
- **THEN** отчёт содержит итог по каждому документу манифеста

#### Scenario: Изменённый документ заменяет прежнюю версию

- **WHEN** содержимое документа изменилось
- **THEN** после переиндексации в базе остаются только чанки новой версии

#### Scenario: Прерванная переиндексация не выдаётся за успешную

- **WHEN** переиндексация прерывается
- **THEN** система сообщает об ошибке и не помечает индекс как успешно перестроенный
