# Design

## Context

См. `proposal.md` — Why. Здесь только состояние и ограничения, которые влияют на подход.

- Репозиторий — скелет: `app/` почти пуст, есть `config.py`, Docker Compose с PostgreSQL, Qdrant, Alembic и Caddy, зависимости в `pyproject.toml`.
- Корпус — около 10 авторских учебно-методических материалов на русском. Три пилотных файла уже лежат в `data/kb/raw/`: MD, DOCX и PDF с текстовым слоем, заголовками и таблицами.
- Оценка — 30 вопросов, ответы на которые есть в корпусе, плюс отказ на вопросах вне базы.
- LLM и эмбеддинги — OpenAI-совместимый протокол. В разработке LM Studio, в продакшене облачный провайдер; приложение не держит модели в памяти.
- Ограничения: Python 3.14, один разработчик, учебный срок, развёртывание на VPS без GPU.

## Goals / Non-Goals

**Goals:**

- Работающий RAG-пайплайн: корпус -> Markdown -> чанки -> эмбеддинги -> retrieval -> ответ с цитатами.
- Multi-turn диалог с переформулировкой поискового запроса.
- Честный отказ, когда в базе нет ответа.
- Веб-чат с регистрацией, историей и карточкой источника.
- Измеримая оценка качества на 30 вопросах и отчёт.
- Развёртывание через Docker Compose и HTTPS.

**Non-Goals:**

- OCR сканированных PDF.
- Агентный роутинг «идти в базу или нет»: retrieval выполняется всегда.
- Hybrid search и reranker в первой версии.
- Fine-tuning, Telegram-бот, мобильное приложение, SSO УРФУ.
- Публикация полных текстов ГОСТов и книг.
- Админ-CMS и гранулярные роли в первой версии.

## Decisions

### 1. Always-retrieve + query rewrite

На каждом ходу диалога выполняется retrieval. Перед поиском последний вопрос переписывается в самостоятельный запрос с учётом последних 3–5 сообщений. Если rewrite недоступен, fallback — склейка последнего вопроса с предыдущим вопросом пользователя.

**Почему:** решение «идти в базу» всегда «да» — это главное обещание продукта. Сложность не в факте retrieval, а в том, с чем в него идти.

**Альтернативы:** поиск по последнему сообщению ломается на уточнениях («а какие у него роли?»); агентный роутинг добавляет ветку, где ответ не основан на базе, и требует отдельной оценки роутера.

### 2. Dense-поиск в Qdrant, hybrid и reranker — позже

Первая версия: dense-векторы, top-k 5–8, порог релевантности. Hybrid (dense + BM25) и cross-encoder reranker добавляются только если eval покажет провалы на точных терминах и аббревиатурах.

**Почему:** корпус маленький, Qdrant уже в скелете, dense-поиск проще отлаживать.

**Альтернативы:** hybrid с первого дня — больше движущихся частей; reranker — ещё одна модель в памяти и задержка.

### 3. Чанкинг по заголовкам с нормализацией и склейкой

Пайплайн: Markdown -> очистка -> разбиение по заголовкам -> склейка слишком коротких секций -> рекурсивное дробление длинных секций до лимита токенов с перекрытием ~15%.

Нормализация обязательна: в DOCX разделы — H1, в MD и PDF — H2. Чанкер определяет верхний уровень заголовков в документе и строит `heading_path` относительно него, а не полагается на абсолютный уровень.

**Почему:** заголовки дают структуру и хорошие цитаты; фиксированное окно рвёт смысл и таблицы.

**Альтернативы:** фиксированное окно по символам — просто, но теряет структуру; семантический чанкинг — дороже и нестабилен на коротких документах.

### 4. Markdown — канонический промежуточный формат

PDF и DOCX конвертируются в Markdown один раз. Дальше чанкинг, цитаты и предпросмотр работают с одним представлением. Исходный файл сохраняется.

**Почему:** одна ветка парсинга вместо четырёх; проще отлаживать.

**Альтернативы:** парсить каждый формат на лету — четыре набора багов и несогласованные цитаты.

### 5. Таблицы — HTML внутри Markdown

Таблицы из DOCX и PDF при конвертации превращаются в нативные HTML-блоки (`<table>`/`<thead>`, `<tr>`, `<th>`, `<td>`) внутри канонического Markdown, а не в pipe-таблицы. Чанкер обрабатывает таблицу как неделимый блок: она целиком входит в один чанк; при дроблении длинной таблицы разрывы идут только между строками с повторением заголовка — таблица никогда не обрывается посреди строки.

**Почему:** HTML-таблица стабильнее pipe-формата (многострочные ячейки не ломают разметку), однозначно хранится и одинаково хорошо понимается моделью; неделимость блока исключает обрыв таблицы на середине чанка, из которого рождаются неверные ответы.

**Альтернативы:** pipe-таблицы — привычнее в исходнике, но хрупки к многострочным ячейкам и не дают контроля границ строк при дроблении чанков.

### 6. PostgreSQL — источник истины, Qdrant — производный индекс

PostgreSQL хранит пользователей, сессии, диалоги, сообщения, документы и статусы. Qdrant хранит векторы и payload чанков. Текст чанка дублируется в payload для цитат; исходный Markdown остаётся в `data/kb/processed/`.

**Почему:** транзакции и реляционные связи — в PostgreSQL; векторный поиск — в Qdrant. Это же демонстрирует «выбрали и настроили векторную БД».

**Альтернативы:** только Qdrant — нет транзакций и удобных связей; pgvector — меньше соответствия заданию и сложнее hybrid.

### 7. LLM-шлюз на OpenAI-совместимом протоколе

Один интерфейс для chat completions и embeddings. Настройки `LLM_*` и `EMBEDDING_*` раздельные: можно сменить провайдера, URL, ключ и модель без правки кода. В разработке — LM Studio, в продакшене — OpenRouter: `LLM_BASE_URL` и `EMBEDDING_BASE_URL` указывают на `https://openrouter.ai/api/v1`, ключ — из `.env` (значения зафиксированы в `.env.example`).

**Почему:** локальная модель для тестов, облачная для качества и VPS без GPU; замена — вопрос конфига.

**Альтернативы:** провайдер-специфичные SDK — привязка; держать модель в приложении — RAM/GPU на VPS.

### 8. Серверные сессии и Argon2id

Регистрация: email, пароль, подтверждение пароля, без письма. Пароль хранится как Argon2id-хеш. Вход создаёт серверную сессию: случайный токен, в базе — хеш, в браузере — HttpOnly-cookie (SameSite=Lax, Secure в продакшене). Выход удаляет сессию. TTL — из конфига.

**Почему:** предсказуемый logout и отзыв сессий, простой код.

**Альтернативы:** JWT в localStorage — XSS и невозможность отзыва; JWT в HttpOnly-cookie — сложнее отзыв и ротация.

### 9. Jinja2 + HTMX + SSE, без SPA

Серверный рендеринг страниц, частичные обновления через HTMX, потоковая выдача ответа через SSE. Отдельной сборки фронтенда нет.

**Почему:** меньше кода и инфраструктуры, выглядит как сервис, достаточно для чата и истории.

**Альтернативы:** React — лишняя сборка для MVP; Streamlit — не выглядит как продуктовый сервис.

### 10. Оценка качества — first-class артефакт

Датасет: 30 вопросов с эталонным ответом и источником (документ + раздел), 5 вопросов вне базы, 3–5 multi-turn диалогов. Ручная шкала 0/1/2:

- 2 — ответ верный, источник указывает на фрагмент с ответом;
- 1 — ответ частично верный или источник слабый;
- 0 — ответ неверный, выдуманный или отказ при наличии ответа.

Приёмка: не менее 80% двоек на 30 вопросах, не менее 4/5 отказов, не менее 4/5 корректных multi-turn. Eval runner вызывает тот же пайплайн, что и чат, и пишет `eval/report.md`.

**Почему:** проверяет и ответ, и источник; 30 вопросов дешевле проверить вручную, чем настраивать LLM-судью. Критерий «ответил на 30 из 30» проверяет покрытие, а не качество.

**Альтернативы:** RAGAS и LLM-судья — дороже и менее надёжны на маленькой выборке; бинарная шкала — теряет «частично верно».

### 11. Ingestion CLI first, админ-UI — позже

Первая версия: скрипт читает `data/kb/raw/`, конвертирует, чистит, чанкует, считает эмбеддинги и пишет в Qdrant. Статусы и причины ошибок — в PostgreSQL и отчёте. Админ-страница — после того, как ядро RAG доказано на eval.

**Почему:** критический путь — корпус и качество ответов, а не форма загрузки.

**Альтернативы:** админка с первого дня — распыление; ручные вставки в БД — ошибки и отсутствие воспроизводимости.

### 12. Docker Compose + Caddy; продакшен без GPU

Сервисы: PostgreSQL, Qdrant, migrate, app, Caddy (prod-профиль). В продакшене приложение и БД на VPS, LLM и эмбеддинги — облачный API. Health-check показывает состояние БД, Qdrant и базы знаний.

**Почему:** скелет уже это предполагает; VPS без GPU дешевле и проще.

**Альтернативы:** GPU-VPS с локальной моделью — дорого; локальный запуск — не выполняет критерий «развёрнут и доступен».

### 13. Порядок работ — вертикальный срез, не «сначала оболочка»

M0: 3 файла, 3–5 вопросов, ответ с цитатой. M1: 10 документов, retrieval, отказ. M2: веб-чат, история, карточка источника. M3: auth, поиск по истории, оценка ответа. M4: 30 вопросов, отчёт, деплой. M5: админка, reindex, полировка.

**Почему:** парсинг PDF и качество локальной модели — самые рискованные места; их нужно проверить на первом документе, а не на двадцатом.

**Альтернативы:** сначала auth/UI — красивый сервис, который может не отвечать по базе.

## Risks / Trade-offs

| Риск | Смягчение |
|---|---|
| Корпус узкий или не покрывает 30 вопросов | Контракт на документ, матрица «3 вопроса на документ», ранний M0 |
| PDF без текстового слоя или потеря заголовков | Проверка text layer, отбраковка сканов, ручной просмотр processed Markdown |
| Разные уровни заголовков ломают чанкинг | Нормализация относительно верхнего уровня документа, склейка коротких секций |
| Локальная 9B-модель слаба на русском или медленная | Ранний замер TTFT и качества на 5 вопросах, LLM-шлюз, облачный fallback |
| Галлюцинации при уверенном тоне | Порог retrieval + промпт «только по контексту» + цитаты + вопросы вне базы в eval |
| Потеря темы в multi-turn | Query rewrite, 3–5 диалогов в eval |
| Расползание объёма (auth, админка, reindex) | M0–M5, ядро RAG раньше оболочки, админка после eval |
| Маленький корпус воспринимается как «всё знает» | Честная формулировка продукта: отвечает по загруженной базе, вне базы отказывается |
| Авторские методички принимают за ГОСТы | В карточке источника указывать тип и название материала, не выдавать за первоисточник |
| Права на тексты | `data/kb/` вне git, не публиковать полные тексты, цитировать фрагменты |
| LLM или эмбеддинги недоступны | Понятная ошибка деградации, история и вопрос сохраняются, health-check `degraded` |
| Утечка секретов | `.env` вне git, Argon2id, HttpOnly, CSRF, rate limit |

## Migration Plan

Проект greenfield, миграции данных нет.

1. M0: прогнать 3 пилотных файла через конвертацию, чанкинг, эмбеддинги и retrieval; проверить 3–5 вопросов и цитаты.
2. M1: подключить 10 документов, настроить порог отказа, собрать 30 вопросов.
3. M2–M3: добавить веб-чат, историю, auth и оценку ответа.
4. M4: прогнать eval, зафиксировать отчёт, развернуть на VPS.
5. M5: админка, повторная индексация, полировка.

Повторная индексация в первой версии — полная пересборка коллекции. Для 10 документов это быстро; blue/green через алиас Qdrant — опционально позже. Откат развёртывания — предыдущий образ приложения и дамп PostgreSQL.
